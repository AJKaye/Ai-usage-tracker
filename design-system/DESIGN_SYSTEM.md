# AI Usage Tracker — Design System (North Star)

> **The single source of truth for how the product looks and behaves.** Every feature, in every phase, styles against this system — no feature invents its own colors, spacing, or components. Read this first; then the specs in `specs/`. Companion to the project's [`PROJECT_CONTEXT.md`](../PROJECT_CONTEXT.md) and [`DEVELOPMENT_PLAN.md`](../DEVELOPMENT_PLAN.md).

**Last updated:** 2026-08-04 · **Status:** authored (tokens + specs + validator + styleguide seed complete; Style Dictionary pipeline lands in Phase 0).

## 1. Why this exists

An enterprise product built over 11 phases by many hands will drift visually unless there is one central styling authority. This design system is that authority, and it is built so **one change propagates to every feature** — the user's core requirement. It also delivers the three cross-cutting product needs: **light + dark**, **WCAG 2.1 AA**, and **per-tenant white-label theming**.

## 2. The mechanism (how "change once → applies everywhere" works)

**CSS custom properties are the distribution layer.** Every component references role tokens — `var(--color-bg-surface)`, `var(--space-5)`, `var(--btn-radius)` — and **never** a raw hex or px. A theme (base, dark, or a tenant) is just a scope that re-points those variables. Swap the scope → the whole app restyles with **zero component edits**. Change a primitive → every layer above recomputes. That is the entire trick, and it's enforced (§6), not merely encouraged.

## 3. Three-tier token layering

| Layer | File | What | Rule |
|-------|------|------|------|
| **Primitive** | `tokens/primitive.tokens.json` | raw brand-neutral scales | components never touch these |
| **Semantic** | `tokens/semantic.tokens.json` | role aliases carrying light + dark | **never a raw hex — always alias a primitive** |
| **Component** | `tokens/component.tokens.json` | per-component knobs | consume only semantics |

Generated outputs live in `dist/`: **`tokens.css`** (the primary artifact — CSS vars for `:root`, `[data-theme]`, and dark), **`tokens.ts`** (typed refs + `applyTheme()`), `tokens.json` (tooling). `dist/` is generated by Style Dictionary from `tokens/**` — see `scripts/build.md`. Full architecture + naming + how-to-change: [`specs/tokens.md`](./specs/tokens.md).

## 4. Brand posture & theming (decisions B1 + B2)

- **B1 — fully neutral base.** The base theme is a professional, vendor-independent neutral. No company's brand is baked into the foundation. SS&C ships only as *one example theme* (`tokens/themes/example-ssc.json`), exactly like any tenant.
- **B2 — generic, swappable chart palette.** Charts default to an accessibility-validated generic palette (`tokens/chart-palette.json`); a tenant swaps it for brand hues and must pass the validator.
- **White-label = extended themes.** A tenant theme overrides only ~a dozen brand values and inherits the entire system. Adding a tenant is copy-`_template.json` → set brand ramp → validate → build. Procedure in [`specs/tokens.md`](./specs/tokens.md).

## 6. Enforcement (what keeps it coherent)

The system stays real because CI fails the build otherwise:
1. **No raw values in components** — stylelint rejects hex/px in component styles; only `var(--token)`.
2. **Palette gate** — `scripts/validate_palette.mjs` runs on the default + every tenant palette (light + dark). CVD ΔE, normal-vision floor 15, band, chroma, 3:1 contrast — exit 1 fails CI.
3. **Contrast** — semantic text-on-surface pairs asserted AA in both modes.
4. **Visual + a11y regression** — axe + Playwright/Chromatic against the styleguide/Storybook (Storybook added Phase 8).
5. **Stale dist** — CI rebuilds `dist/` and fails on a diff.

## 7. How this plugs into the 11-phase plan

- **Phase 0** — token scaffold + Style Dictionary build + stylelint/validator CI gates land here, so every later phase inherits them.
- **Phases 1–7** — any internal/admin UI styles against `dist/tokens.css`; no ad-hoc styling.
- **Phase 8 (Web UI)** — the React SPA imports `dist/tokens.css` + `dist/tokens.ts`; Storybook becomes the interactive gallery; the **Regulatory Governance page** is styled entirely from tokens like every other view.
- **Ongoing** — new components extend the token set (add primitive → semantic → component), never hardcode.

## 8. Provenance

Grounded in the local `design` skill and `dataviz` skill, with exact values extracted and cited in the specs: token architecture from `figma-generate-library` + `color-expert`; WCAG/dark/component rules from `web-design-guidelines` + `ui-ux-pro-max`; motion from `design-motion-principles`; chart palette + validator from `dataviz`; the SS&C example theme from `design/SSCBranding`. Three gaps in the source brand kit were filled here: **dark mode**, an **elevation scale**, and a **reconciled spacing ramp** (see `specs/tokens.md`).

## 9. Rules for future agents

1. Style against **tokens only** — if you're typing a hex or px into a component, stop and use/add a token.
2. New color/spacing/radius → add the **primitive** first, then a **semantic** alias, then (if needed) a **component** token. Update `dist/` via the build.
3. New chart → invoke the **`dataviz`** skill, follow `specs/charts.md`, and run the validator before shipping any non-default palette.
4. New tenant → copy `_template.json`, fill the brand ramp, validate, build. Never fork the base.
5. Every interactive thing implements the full **state matrix** (`specs/components.md`) and is **keyboard + AA** (`specs/accessibility.md`).
6. Verify a design change in the **styleguide** (theme-switch it) before wiring it into features — that's the "applies everywhere" proof.
